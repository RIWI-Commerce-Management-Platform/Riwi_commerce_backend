## What was implemented

### 1. `clients` module

Follows the standard 4-layer shape (`src/modules/clients/`):

- **Domain** — `Client` entity (mutates in place: `activate()`/`deactivate()`/`update()`, matching the `zones` convention), `ClientRepository` port, `ClientFilterCriteria`, `domain/errors/`: `ClientNitAlreadyExistsError`, `ClientNotFoundError`.
- **Application** — `CreateClientUseCase`, `UpdateClientUseCase`, `ToggleClientStatusUseCase`, `FindClientsUseCase`, `GetClientByIdUseCase`; `application/ports/geocoding.port.ts` (`GeocodingPort`) as a second, module-local port alongside the repository.
- **Infrastructure** — `ClientOrmEntity` (table `clients`), `ClientMapper`, `TypeOrmClientRepository` (query-builder-based search/filter/pagination), `NominatimGeocodingAdapter` (calls OpenStreetMap's Nominatim API), migration `1792505831167-CreateClientsTable`.
- **Presentation** — `ClientsController`: `GET /clients` (search + filters + pagination), `GET /clients/:id`, `POST /clients`, `PATCH /clients/:id`, `PATCH /clients/:id/status`; request/response DTOs, Swagger-documented.

### 2. NIT uniqueness, geocoding, soft-deactivation

- `CreateClientUseCase`/`UpdateClientUseCase` check `findByNit()` and throw `ClientNitAlreadyExistsError` (→ `409`) on conflict, excluding the client's own row on update.
- If `latitude`/`longitude` are omitted on create, or become stale because `address`/`municipality`/`department` changed on update, the use case calls `GeocodingPort.geocode()`; `NominatimGeocodingAdapter` queries `nominatim.openstreetmap.org` with a 5s timeout and degrades to `null` (not an error) on any non-OK response, empty result, or network failure — covered by `nominatim-geocoding.adapter.spec.ts` (mocked `fetch`, including a 503 and a rejected fetch).
- There is no delete endpoint. `PATCH /clients/:id/status` calls `Client.activate()`/`deactivate()` (toggles current state if `isActive` is omitted from the body) — matches "inactivar en vez de borrar".

### 3. Search, filters, pagination — also satisfies HU-12

`GET /clients` implements the exact contract HU-12 asks for ("Búsqueda por NIT, razón social o nombre; filtros por zona, tipo, municipio y potencial; paginado"), plus an `isActive` filter: `FindClientsQueryDto` → `ClientFilterCriteria` → `TypeOrmClientRepository.findPaginated()` (case-insensitive `LIKE` over nit/business_name/commercial_name, exact-match filters, `ORDER BY created_at DESC`). This was built as part of HU-11 rather than a separate story — **worth flagging to the team so HU-12 gets marked accordingly instead of re-implemented.**

A new shared port, `src/shared/pagination/` (`PaginationQueryDto`, `PaginatedResult`/`PaginationMeta`, `PaginatedResponseDto` with a static `.create(result, mapper)` helper), was introduced for this — the first shared pagination DTO in the codebase (CLAUDE.md previously listed this as "not yet implemented"; update it).

### 4. IDs and FKs

`Client.id` is DB-generated auto-increment (`@PrimaryGeneratedColumn()`), matching the `quotes`/`visit` convention. `zoneId`/`clientTypeId`/`potentialId`/`clientStatusId` are `uuid` columns (matching `zones`' legacy UUID ids) but **not declared as DB foreign keys** — only `zones` exists as a real table today; `clientTypeId`/`potentialId`/`clientStatusId` reference catalogs that HU-14 ("administrar catálogos") hasn't created yet. The API currently accepts any UUID string for those three fields with no referential check.

## Not yet verified / open items

- **`npm run migration:run` and `npm run test:e2e` against a live Postgres** — not run; Docker daemon isn't reachable in this environment. `.env.example`/`docker-compose.yaml` were also updated in this merge to add `POSTGRES_HOST_PORT` (lets the host map Postgres to a different port than the container's `POSTGRES_PORT`, e.g. when a local Postgres already holds 5432) — run `docker compose up` then `npm run migration:run` to confirm the `clients` table creates cleanly.
- **Merge not yet committed.** `git status` shows conflicts resolved but the merge commit not made yet (`MERGE_HEAD` present). Two tracked files have **unstaged** changes on top of the staged merge resolution — check these before running `git commit`:
  - `src/app.module.ts` — the staged/index version still does **not** import or register `ClientsModule`; only the working tree has it. If you commit right now without `git add src/app.module.ts`, the merge commit will ship the `clients` module unwired — none of its routes will be reachable at runtime even though build/tests pass.
  - `src/modules/clients/presentation/clients.controller.ts` — the staged version has `@Put(':id')` on the update route; the working tree has it manually corrected to `@Patch(':id')` (correct, since every field in `UpdateClientDto` is optional — a partial update). Stage this file too or the fix is lost.
- **`src/shared/clients/` still returns `NullClientReader`.** This HU-11 module (`src/modules/clients/`) is a separate thing from the `ClientReader` port the `visit` module depends on (`src/shared/clients/domain/client-reader.ts`) — implementing the latter against this new module (and repointing `ClientsModule`'s `useClass` in `src/shared/clients/clients.module.ts`) is a follow-up, not done here.
- **Naming collision:** both `src/modules/clients/clients.module.ts` and `src/shared/clients/clients.module.ts` export a class named `ClientsModule`. No compile error today (each is only imported from a different file via a different relative path), but it's confusing and will collide if anything ever needs to import both — consider renaming the shared port's module (e.g. `ClientReaderModule`) when wiring the real adapter above.
