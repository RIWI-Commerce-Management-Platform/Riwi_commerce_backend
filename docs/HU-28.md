# HU-28 — Attach a photo or document to a visit

**Owner:** Camilo · **Epic:** E4 — Agenda, visits and follow-up · **Priority:** High

**Source:** `docs/Comercial360_Historias_y_Reparto_v2.pdf`, page 7

> As an advisor, I want to attach a photo or document to a visit.

## Acceptance criteria

| Criterion                                                           | Status                                                                                          |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Upload a photo or document using the shared S3 file-storage service | ✅ Backend implemented                                                                          |
| Show an attachment thumbnail or link                                | 🟡 Backend supplies temporary preview/download URLs; frontend is not present in this repository |

## What was implemented

### 1. Visit attachment endpoints

| Method and path                | Behavior                                             |
| ------------------------------ | ---------------------------------------------------- |
| `POST /visits/:id/attachments` | Upload one multipart file using the `file` field     |
| `GET /visits/:id/attachments`  | List attachments and return a temporary URL for each |

Both endpoints use the existing `CurrentAdvisorProvider` and require the visit to belong to the current advisor. A missing visit or a visit owned by another advisor returns `404`.

Uploads are limited to 10 MiB. The shared `FileStorageService` remains responsible for the accepted MIME types, S3 upload, signed URLs, and deletion. Its accepted types are PDF, JPEG, PNG, WebP, CSV, and Excel spreadsheets. The returned response contains the original filename, MIME type, size, creation timestamp, and temporary URL; it does not expose the S3 storage key.

Example multipart upload:

```bash
curl -X POST http://localhost:3000/visits/1/attachments \
  -H "x-user-id: 20" \
  -F "file=@visit-photo.jpg"
```

The temporary URL expires after the shared service's default one-hour signing period. Images and supported documents can be previewed or downloaded by a client that can access the URL.

### 2. Persistence and failure handling

- Attachment metadata and the private S3 object key are stored in `visit_attachments`, separate from the visit row.
- The table has a foreign key to `visits` with `ON DELETE CASCADE` and an index on `visit_id`.
- If metadata persistence fails after an S3 upload, the uploaded object is deleted. If cleanup also fails, both errors are surfaced.
- The storage key is not returned by the presentation DTO.

### 3. Module integration

The implementation reuses `VisitDao.findByIdAndAdvisor()` and the shared `FileStorageModule`. It adds only an attachment DAO, entity, TypeORM mapping, migration, and the upload/list use cases required for this story. No parallel S3 client or visit-authorization path was introduced.

## Not implemented in this repository

- The visual attachment control and thumbnail/link rendering belong to the frontend, which is not part of this backend repository.
- A live PostgreSQL migration and S3 upload were not run as part of the automated test suite.
- `CurrentAdvisorProvider` still uses the temporary `x-user-id` header; the application's existing session guard and advisor-ID mapping remain a separate authentication integration.
