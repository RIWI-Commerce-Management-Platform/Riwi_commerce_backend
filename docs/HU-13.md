# HU-13 — Manage client contacts

**Owner:** Yesid · **Epic:** E2 — Clientes, catálogos y bitácora · **Priority:** Alta
**Source:** `docs/Comercial360_Historias_y_Reparto_v2.pdf`

> Como asesor, quiero gestionar los contactos de un cliente, para saber con quién hablar.

## Acceptance criteria

| Criterion | Status |
|---|---|

## What was implemented

### 1. `ClientContact`, as a sub-resource of `clients`

Lives inside the existing `src/modules/clients/` module rather than as a separate top-level module (contacts have no independent lifecycle — they're always scoped to a client):

- **Domain** — `ClientContact` entity (mutates in place, same convention as `Client`/`zones`: `markAsPrimary()`, `demoteFromPrimary()`, `activate()`, `deactivate()`, `update()`), `ClientContactRepository` port (`save`, `findById`, `findByClientId`, `unsetPrimaryByClientId`), `ClientContactNotFoundError`.
- **Application** — `CreateClientContactUseCase`, `UpdateClientContactUseCase`, `ListClientContactsUseCase`, `SetPrimaryContactUseCase`, `DeleteClientContactUseCase`.
- **Infrastructure** — `ClientContactOrmEntity` (table `client_contacts`, `@ManyToOne` → `ClientOrmEntity` with `onDelete: 'CASCADE'`), `ClientContactMapper`, `TypeOrmClientContactRepository`, migration `1792505831168-CreateClientContactsTable`.
- **Presentation** — `ClientContactsController` mounted at `clients/:clientId/contacts`: `POST /`, `GET /`, `PATCH /:contactId`, `PATCH /:contactId/primary`, `DELETE /:contactId` (soft delete); DTOs and responses Swagger-documented. Registered in `ClientsModule` alongside `ClientsController`.

### 2. Single-primary-contact rule

Enforced at the use-case layer via `ClientContactRepository.unsetPrimaryByClientId(clientId, excludeContactId?)` (a single batched `UPDATE ... SET is_primary = false WHERE client_id = :clientId [AND id != :excludeContactId]`, not a read-then-write):

- `CreateClientContactUseCase` — a new contact becomes primary if explicitly requested (`isPrimary: true`) **or** if it's the client's first contact; either way, any existing primary is demoted first.
- `UpdateClientContactUseCase` — promoting a contact to primary (`isPrimary: true` and it wasn't already) demotes the previous primary first.
- `SetPrimaryContactUseCase` — a dedicated `PATCH :contactId/primary` fast path; no-ops if the contact is already primary.
- `DeleteClientContactUseCase` — soft-deletes via `deactivate()`, which also clears `isPrimary` (see `ClientContact.deactivate()`), so a removed contact can never remain the client's primary.

`TypeOrmClientContactRepository.findByClientId()` filters `isActive: true` and orders `isPrimary DESC, createdAt ASC`, so `GET .../contacts` only lists active contacts with the primary one listed first, matching the acceptance criterion.

### 3. First real DB-level foreign key in the codebase

The migration adds an actual Postgres `FOREIGN KEY (client_id) REFERENCES clients(id) ON DELETE CASCADE` — unlike `clients.zone_id`/`client_type_id`/`potential_id`/`client_status_id`, which are plain `uuid` columns with no FK constraint (see `docs/HU-11.md`). Deleting a client row would cascade-delete its contacts (moot in practice since clients are only ever soft-deactivated, never hard-deleted).

### 4. `DELETE` instead of `PATCH .../status`

Unlike `clients` (`PATCH /clients/:id/status` to toggle active/inactive), contacts expose a `DELETE /clients/:clientId/contacts/:contactId` endpoint. It does not actually delete the row — `DeleteClientContactUseCase` calls `deactivate()` and persists — but the HTTP verb reads as a hard delete. Swagger does label it "Deactivate / soft delete a client contact," but there's no reactivation endpoint for contacts (unlike clients' `PATCH .../status`, which toggles both ways), so once deleted a contact can't be brought back through the API today.

## Verified in this environment

- `npm run lint` (`oxlint --type-aware`) — 0 errors (a handful of pre-existing-style `warning`s in spec files — unused import in `client-contacts.controller.spec.ts`, `unbound-method` style warnings across the new `*.spec.ts` files — none fail the build).

### Test coverage gap worth knowing about

Of the 5 new use cases, only `CreateClientContactUseCase` and `UpdateClientContactUseCase` have dedicated use-case-level spec files. `DeleteClientContactUseCase`, `ListClientContactsUseCase`, and `SetPrimaryContactUseCase` are only exercised indirectly through `client-contacts.controller.spec.ts`, which mocks the use cases and checks controller wiring — it does not verify their internal logic (e.g. that `SetPrimaryContactUseCase` actually calls `unsetPrimaryByClientId` with the right exclusion, or that `DeleteClientContactUseCase` clears `isPrimary` on deactivate). There's also no `ClientContactMapper` spec or `TypeOrmClientContactRepository` spec. `docs/USER_STORIES_IMPLEMENTATION.md` (Yesid's own consolidated write-up for E2) describes this as "fully isolated test coverage across domain entities, use cases, mappers, and controllers" — that's accurate for the entity and controller layers, but overstates the use-case/mapper/repository layers as described above.
