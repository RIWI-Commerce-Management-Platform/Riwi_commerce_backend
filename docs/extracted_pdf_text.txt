Resumen del proyecto
Construimos Comercial 360, un gestor comercial (clientes, rutas, visitas, seguimientos,
cotizaciones, pedidos y KPI), y lo sustentamos desplegado en AWS el ​Oct 26, 2026 .
Tenemos 6 días hábiles; cada persona es dueña de un módulo completo (backend +
frontend) para poder explicarlo en la sustentación.
Requisitos obligatorios que no pueden faltar el día de la demo:
Backend NestJS con arquitectura Clean Architecture (el enunciado acepta Hexagonal
o Clean; el equipo eligió Clean)
Persistencia con TypeORM sobre PostgreSQL en Amazon RDS
Autenticación con Better Auth
Mapa de visitas con OpenStreetMap (Leaflet)
Dashboard de KPI, agenda del asesor, bitácora de actividades, cotizaciones simuladas,
exportación CSV
Todos los archivos (fotos, documentos) en Amazon S3; la BD guarda solo la referencia
(key)
App desplegada en EC2 con Jenkins en la misma instancia, conectado a GitHub, y
demo de un despliegue en vivo
Repo sin archivos multimedia, credenciales ni .env
Los 5 diseños entregados (login, dashboard, registrar visita, creación de rutas) son la
referencia visual del frontend. Roles que aparecen en los diseños: Asesor Comercial y
Director Regional; añadimos Administrador.

Equipo y responsabilidades
El reparto es por módulo vertical: cada dev hace dominio, casos de uso, repositorios
TypeORM, controlador, Swagger y pantallas de su módulo. Así nadie bloquea a nadie y
cada uno sustenta lo suyo.

Reglas de trabajo
Clean Architecture. Todos siguen la misma estructura por módulo, con 4 capas y las
dependencias apuntando siempre hacia adentro; Luis la deja creada el lunes con el
módulo de ejemplo zones .
src/
shared/
# pagination, exceptions, ActivityLogService,
FileStorageService (abstract classes)
modules/
clients/
domain/
# entities, value objects, repository
interfaces (abstract classes), domain errors
application/
# use cases (CreateClientUseCase, ...),
input/output DTOs, service interfaces
infrastructure/
# TypeORM entities + mappers, repository
implementations, migrations, external clients
presentation/
decorators

# controllers, request/response DTOs, Swagger

clients.module.ts
implementation (DI)

# binds each abstract class to its

Regla de dependencias: domain no importa nada externo (ni NestJS ni TypeORM);
application solo importa domain ; infrastructure y presentation dependen de

las capas internas, nunca al revés.
Los casos de uso dependen de clases abstractas (ej. ClientRepository ) y el
*.module.ts las enlaza con su implementación TypeORM; las entidades de dominio no

son las entidades de TypeORM, un mapper traduce entre ambas. Un módulo usa a otro
solo por esas abstracciones (ej. visitas llama a ActivityLogService , nunca al
repositorio de historial).
Cada dev crea las migraciones de sus tablas; nombres de tablas y columnas en inglés y
snake_case .

Código, comentarios, Swagger y mensajes de error en inglés.
Git y GitHub.
Ramas: main (lo que despliega Jenkins), develop (integración), feature/HU-XXdescripcion-corta .
PR a develop con al menos 1 aprobación (Luis o el dev del módulo vecino); Luis pasa
develop a main al final de cada día.
