## What was implemented / proposed

### 1. Folder structure and dependency rule

The visits module should follow the project's Clean Architecture
convention:

``` text
src/
  shared/
    # Shared services, configuration and cross-cutting utilities
  modules/
    visits/
      domain/
        entities/
        repositories/
      application/
        use-cases/
      infrastructure/
        entities/
        mappers/
        repositories/
        migrations/
      presentation/
        controllers/
        dtos/
      visits.module.ts
```

-   **Domain:** visit rules and repository contract; should not import
    NestJS or TypeORM.
-   **Application:** use cases for listing an agenda, reading visit
    details, starting a visit and registering a result.
-   **Infrastructure:** TypeORM entities, mapping and repository
    implementation.
-   **Presentation:** REST controller, validation DTOs and Swagger
    documentation.
-   **Module wiring:** binds the repository abstraction to its TypeORM
    implementation through dependency injection.

Follow the exact naming, formatting, migration and testing conventions
already used by `src/modules/zones/`. Do not create a second visit
table/entity if Alejandro or another teammate has already created it.

### 3. Agenda and visit lifecycle

The application should support the following flow:

1.  The authenticated advisor opens the daily or weekly agenda.
2.  The API returns only visits that the advisor is allowed to see,
    ordered by scheduled date/time.
3.  The advisor opens a visit and sees the visit plus related
    customer/contact information.
4.  The advisor starts the visit.
5.  When the visit ends, the advisor records actual date, start/end
    times, one or more catalog results, observations (up to 500
    characters), and the final status.
6.  The API saves the visit and its result rows and writes the
    corresponding event to the customer activity log.

The domain draft models `PENDING`, `IN_PROGRESS`, `VISITED`,
`RESCHEDULED`, and `NOT_VISITED`. Confirm the final enum values with the
team and the existing database schema.

### 4. Persistence and database compatibility

The functional model identifies these tables for this module:

-   `VISITA`: scheduled/actual visit information, customer, advisor,
    route and visit status.
-   `RESULTADO_VISITA`: catalog of possible visit results.
-   `VISITA_RESULTADO`: relationship between a visit and one or more
    results, including an observation.
-   `SEGUIMIENTO`: follow-up tasks for HU-25 (not part of HU-23/HU-24
    implementation unless agreed otherwise).

The earlier code draft used English table/column names such as `visits`,
`scheduled_at` and `status`. **Do not apply that draft schema blindly.**
The project convention says database table/column names use English
`snake_case`, while the functional model names the entities in Spanish.
Agree with Luis and Alejandro on the canonical database naming and
existing migrations first.

Before merging, confirm: - Primary-key types and foreign-key names. -
Whether visit rows are created by Alejandro's HU-20 route assignment
flow. - The source of the result catalog and its seed data. - How
start/end times and actual dates are represented in PostgreSQL. - That
`synchronize` remains disabled and schema changes use migrations.

`@ApiTags('Visits')`, `@ApiOperation`, `@ApiParam`, `@ApiQuery`,
`@ApiBody` where applicable, and `@ApiResponse`/`@ApiOkResponse`.
Request DTOs should use the project's established validation approach.

After integration, run the backend and open the Swagger URL configured
in the project (for example, `http://localhost:3000/api`; the actual
route may differ). Confirm that the four routes appear under **Visits**,
inspect the documented request schemas, and execute successful and
failing requests.

**Security note:** a temporary `x-user-id` header, if present in a local
draft, is only a development placeholder. It must not be treated as
authentication or authorization and must not be merged as the final
security mechanism.
