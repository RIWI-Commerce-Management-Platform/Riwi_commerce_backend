convention:

-   **Domain:** visit rules and repository contract; should not import

-   **Presentation:** REST controller, validation DTOs and Swagger
    documentation.
-   **Module wiring:** binds the repository abstraction to its TypeORM
    implementation through dependency injection.

Follow the exact naming, formatting, migration and testing conventions
already used by `src/modules/zones/`. Do not create a second visit
table/entity if Alejandro or another teammate has already created it.

### 3. Agenda and visit lifecycle

The application should support the following flow:

1.  The authenticated advisor opens the daily or weekly agenda.
2.  The API returns only visits that the advisor is allowed to see,
    ordered by scheduled date/time.
3.  The advisor opens a visit and sees the visit plus related
    customer/contact information.
4.  The advisor starts the visit.
5.  When the visit ends, the advisor records actual date, start/end
    times, one or more catalog results, observations (up to 500
    characters), and the final status.
6.  The API saves the visit and its result rows and writes the
    corresponding event to the customer activity log.

The domain draft models `PENDING`, `IN_PROGRESS`, `VISITED`,
`RESCHEDULED`, and `NOT_VISITED`. Confirm the final enum values with the
team and the existing database schema.

### 4. Persistence and database compatibility

The functional model identifies these tables for this module:

-   `VISITA`: scheduled/actual visit information, customer, advisor,
    route and visit status.
-   `RESULTADO_VISITA`: catalog of possible visit results.
-   `VISITA_RESULTADO`: relationship between a visit and one or more
    results, including an observation.
-   `SEGUIMIENTO`: follow-up tasks for HU-25 (not part of HU-23/HU-24
    implementation unless agreed otherwise).

**Decision taken (agreed with the team): database table and column names
use English `snake_case`**, matching `zones` and `quotes`. The functional
Spanish model names map as follows:

| Functional model | Implemented table | Notes |
| --- | --- | --- |
| `VISITA` | `visits` | id `serial`, `client_id`, `advisor_id`, `route_id`, `scheduled_at timestamptz`, `actual_date date`, `start_time time`, `end_time time`, `status varchar(30)`, `objective`, `observations varchar(500)` |
| `RESULTADO_VISITA` | `visit_results` | result catalog: `id serial`, `name`, `is_active`. **Created empty, no seed** |
| `VISITA_RESULTADO` | `visit_result_links` | `visit_id` FK→`visits` (CASCADE), `result_id` FK→`visit_results` (RESTRICT), `observation`, unique `(visit_id, result_id)` |

The migration is `src/modules/visit/infrastructure/migrations/1792444800000-CreateVisitTables.ts`,
written by hand following the `zones`/`quotes` `createTable` convention.
`synchronize` remains **disabled**; schema changes only go through
migrations.

Open points still to confirm with the team:

    flow (the module does **not** create visits, it only reads the ones
    already assigned; `visits.route_id` is reserved for that flow).
-   The definitive seed data for `visit_results` (see proposal below).

## Integration contracts (delivered vs. pending)

The visit module depends on three capabilities owned by other teammates.
None of them shipped a finalized contract yet. To avoid blocking HU-23/HU-24
and to keep the dependency isolated, each one was introduced as a **port
(abstract class) plus a temporary adapter**. When the real implementation
lands, **only the `useClass` binding in the `*.module.ts` changes**; no use
case, controller or domain file has to be touched.

| Port (stays) | Temporary adapter (replace later) | Owner | What to do when it arrives |
| --- | --- | --- | --- |
| `src/shared/auth/domain/current-advisor.provider.ts` | `src/shared/auth/infrastructure/header-current-advisor.provider.ts` (reads `x-user-id`, marked `TEMPORARY`) | Efraín — E1 / Better Auth | Implement `CurrentAdvisorProvider.extract()` from the real session/JWT and repoint `AuthModule`'s `useClass`. Delete the header adapter. |
| `src/shared/clients/domain/client-reader.ts` | `src/shared/clients/infrastructure/null-client.reader.ts` (returns `null`) | Yesid — E2 / clients | Implement `ClientReader.findById()` against the clients module read service and repoint `ClientsModule`. Delete the null adapter. |
| `src/shared/activity-log/domain/activity-log.service.ts` | `src/shared/activity-log/infrastructure/noop-activity-log.service.ts` (logs to console only) | Yesid — E2 / activity log (HU-15) | Implement `ActivityLogService.record()` against the real log and repoint `ActivityLogModule`. Delete the noop adapter. |

**Important honesty note:** the three abstract classes above are the
*minimum contracts proposed from this module*, not the official signatures
from Efraín or Yesid. If their final signatures differ, adapt the temporary
adapter (or adjust the abstract's method signature); the use cases only
depend on the port, not on the adapter.

The temporary `x-user-id` header in `visit.controller.ts` is a
**development placeholder**. It is documented in Swagger as `deprecated`
and **must not** be treated as authentication. It blocks the "filter visits
by authenticated advisor" acceptance criterion of both HUs.

## Endpoints and Swagger — verification examples

Run the backend (`npm run start:dev`) and open
`http://localhost:3000/docs`, section **Visits**. All four endpoints require
the temporary header `x-user-id: 1`.

The verifiable request/response pairs are:

**1. `GET /visits/agenda?period=day&date=2026-10-20`**

```
GET /visits/agenda?period=day&date=2026-10-20
x-user-id: 1
```

`200` — visits of that day, ordered by `scheduled_at ASC`:

``` json
[
  {
    "id": 1,
    "clientId": 10,
    "routeId": null,
    "scheduledAt": "2026-10-20T09:00:00.000Z",
    "status": "PENDING",
    "objective": "Presentar catálogo"
  }
]
```

`period=week` returns Monday→Sunday of the week containing `date`.
Omitting `date` uses today. A bad format returns `400`.

**2. `GET /visits/1`**

```
GET /visits/1
x-user-id: 1
```

`200` — detail; client fields are `null`/absent until the client contract
exists:

``` json
{
  "id": 1,
  "clientId": 10,
  "scheduledAt": "2026-10-20T09:00:00.000Z",
  "status": "PENDING",
  "objective": "Presentar catálogo",
  "actualDate": null,
  "startTime": null,
  "endTime": null,
  "observations": null,
  "results": []
}
```

`404` if the visit does not exist **or belongs to another advisor**.

**3. `PATCH /visits/1/start`**

```
PATCH /visits/1/start
x-user-id: 1
```

`200` — status becomes `IN_PROGRESS` with `actualDate` and `startTime`.
`400` if the visit is not `PENDING`. `404` if it is not yours / not found.

**4. `PATCH /visits/1/result`**

```
PATCH /visits/1/result
x-user-id: 1
Content-Type: application/json
```

``` json
{
  "endTime": "16:30:00",
  "observations": "Cliente interesado en renovar el contrato anual.",
  "results": [
    { "id": 1 },
    { "id": 2, "observation": "Con seguimiento la próxima semana" }
  ]
}
```

`200` — status becomes `VISITED`, with `endTime`, `observations` and the
resolved `results`. Errors: `400` for observations over 500 characters,
empty results, unknown/inactive result ids or an invalid status transition;
`404` for a foreign/missing visit.

**Security note:** the `x-user-id` header is only a development
placeholder. It must not be treated as authentication or authorization and
must not be merged as the final security mechanism.
