# HU-25 — Schedule a follow-up

**Owner:** Camilo · **Epic:** E4 — Agenda, visits and follow-up · **Priority:** Alta
**Source:** `docs/Comercial360_Historias_y_Reparto_v2.pdf`

> As an advisor, I want to schedule a follow-up so as not to miss the opportunity.

## Acceptance criteria

| Criterion                                                          | Status  |
| ------------------------------------------------------------------ | ------- |
| Store the next date, activity, observation and responsible advisor | ✅ Done |
| Mark a follow-up as completed                                      | ✅ Done |
| Show pending follow-ups in the advisor's agenda                    | ✅ Done |

## What was implemented

### 1. `follow-ups` module

Implemented as an independent module, following the project's layered architecture and the requested DAO convention (`src/modules/follow-ups/`):

- **Domain** — `FollowUp` entity and `FollowUpDao` port under `domain/dao/`.
- **Application** — `CreateFollowUpUseCase`, `CompleteFollowUpUseCase`, and `ListFollowUpsUseCase`.
- **Infrastructure** — `FollowUpOrmEntity`, `FollowUpMapper`, `TypeOrmFollowUpDao` under `infrastructure/dao/`, and migration `1792605000000-CreateFollowUpsTable`.
- **Presentation** — `FollowUpsController`, `CreateFollowUpDto`, and `FollowUpResponseDto`; endpoints are Swagger-documented.
- **Module wiring** — registered in `AppModule`; reuses `VisitDao`, `CurrentAdvisorProvider`, and `ActivityLogService` instead of adding parallel infrastructure.

### 2. Scheduling and completion

`CreateFollowUpUseCase` verifies the visit belongs to the current advisor, validates the calendar date and field lengths, assigns the current advisor as the responsible person, saves the follow-up and records `follow_up.created` through the existing activity-log port.

`CompleteFollowUpUseCase` verifies advisor ownership and marks the item completed. Completing an already completed item is idempotent and does not save it again. A successful state change is recorded as `follow_up.completed` through the existing activity-log port.

The current identity adapter reads the temporary `x-user-id` header. The real Better Auth integration is not part of this story's implementation.

### 3. HTTP endpoints

| Method and path                                           | Behavior                                                       |
| --------------------------------------------------------- | -------------------------------------------------------------- |
| `POST /follow-ups/visits/:visitId`                        | Schedule a follow-up for an authorized visit                   |
| `GET /follow-ups/visits/:visitId`                         | List follow-ups for an authorized visit                        |
| `GET /follow-ups/agenda?date=YYYY-MM-DD&period=day\|week` | List pending follow-ups for the current advisor and date range |
| `PATCH /follow-ups/:id/complete`                          | Mark an advisor-owned follow-up as completed                   |

The agenda filters out completed items and supports day and week periods. Listing by visit includes completed items for history.

### 4. PostgreSQL schema

The migration creates `follow_ups` with `visit_id`, `next_date`, `activity`, nullable `observation`, `responsible_advisor_id`, `completed`, `created_at`, and `updated_at`. `visit_id` has a foreign key to `visits(id)` with `ON DELETE CASCADE`. `synchronize` remains disabled; schema changes are managed through migrations.
