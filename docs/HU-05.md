# HU-05 — Login with email and password

**Owner:** Efraín (E1) · **Priority:** Alta
**Epic:** E1 — Seguridad, Autenticación, Roles y Gestión de Asesores ([Documento Consolidado de Épica](./EPIC-E1-seguridad-autenticacion-efrain.md))
**Source:** `docs/Comercial360_Historias_y_Reparto_v2.pdf`

> Como usuario, quiero iniciar sesión con correo y contraseña, para acceder a la plataforma.
> Criteria: Better Auth en NestJS; login, logout y "Recordarme"; rutas del front protegidas; guard de sesión en el back.

**Status: functionally done for this repo's scope.** `feat/HU-05` is merged into `develop` (commit `257d5fb`). Login/logout/"Recordarme"/session-guard all work, the session guard is now wired app-wide (every route requires a session unless marked `@Public()`), and `AuthController` now matches the rest of the codebase's Clean Architecture convention (one use case per action) — though the guard rollout and the use-case refactor, done in this pass, are **not yet committed** (see "Git" under "Known gaps"). What's left is genuinely out of this repo (the frontend half of the criterion) or explicitly out of scope per `README.md` (linking a session to an `ASESOR`/advisor record) — see "Known gaps".

## What exists

### 1. `auth` module (`src/modules/auth/`)

Now the standard 4-layer shape: `domain/` (`UserRole` enum + 7 domain errors), `application/` (5 use cases, one per controller action), `infrastructure/` (Better Auth's own ORM entities + migrations), `presentation/` (`AuthController`, now a thin orchestrator — each method calls one use case and maps its domain errors to an HTTP exception, matching the `zones`-module convention documented in `CLAUDE.md`).

- **Better Auth setup** (`auth.ts`) — `betterAuth()` configured with `@hedystia/better-auth-typeorm`'s `typeormAdapter(dataSource)`, email/password auth, a 7-day session (`cookieCache` 5 min), and `additionalFields.role`/`additionalFields.zoneId` on the `user` table.
- **Endpoints** (`AuthController`, all under `/auth`):
  | Route | Guard | Description |
  |---|---|---|
  | `POST /auth/login` | `@Public()` | `LoginUseCase` → `auth.api.signInEmail`; forwards Better Auth's `Set-Cookie` (`better-auth.session_token`); `rememberMe` controls persistent vs. session cookie |
  | `POST /auth/register` | `@Public()` | `RegisterUseCase` → `auth.api.signUpEmail`; new users default to role `ASESOR` |
  | `POST /auth/logout` | `@Public()` | `LogoutUseCase` → `auth.api.signOut`; invalidates the session (public so an already-expired cookie can still be cleared without a 401) |
  | `GET /auth/me` | global `SessionGuard` | `GetCurrentUserUseCase`; current user + session, with `role`/`zoneId` re-read from the DB (not trusted from the session payload) |
  | `GET /auth/protected` | global `SessionGuard` | Smoke-test endpoint |
  | `PATCH /auth/users/:userId/role` | global `SessionGuard` + route-level `RolesGuard` (`@Roles(ADMIN)`) | `AssignUserRoleUseCase`; `DIRECTOR_REGIONAL` requires a `zoneId` referencing an existing zone — this is really HU-06, not HU-05 (see "Known gaps") |
  - Better Auth's own native routes are also live and reachable directly, e.g. `POST /api/auth/sign-in/email` (exercised in `test/auth.e2e-spec.ts` section 4). These are mounted by `@thallesp/nestjs-better-auth` as raw Express middleware (`httpAdapter.use(...)`, see its `configure()`), not as NestJS controller routes — so they run **before** and independently of any Nest guard, global or not. `AuthController`'s own routes are a thin wrapper around a subset of the same API with cookie forwarding and our own DTOs/validation.
- **`SessionGuard`** (`guards/session.guard.ts`) — calls `auth.api.getSession()` per request; honors `@Public()` to skip; throws `401` otherwise and attaches `request.session`/`request.user`. Now registered as a global `APP_GUARD` in `AuthModule` (see "Global session guard" below). Unit-tested in `session.guard.spec.ts` (added in this pass).
- **`RolesGuard`** (`guards/roles.guard.ts`) — re-reads the user's `role`/`zoneId` from `UserOrmEntity` (doesn't trust the session payload) and throws `403` if the role isn't in `@Roles(...)`. Stays route-level (only `PATCH /auth/users/:userId/role` needs it); a no-op on any route without `@Roles(...)`. Unit-tested in `roles.guard.spec.ts`.
- **DTO validation** — `LoginDto`/`RegisterDto` now carry `class-validator` decorators (`@IsEmail`, `@IsNotEmpty`, `@MinLength(8)`, etc.), and `AuthController` applies `@UsePipes(new ValidationPipe({ whitelist: true, transform: true }))` at the controller level — following the same pattern `VisitsController` already uses (the only other controller in the repo that does this; most DTOs in the repo have no enforced validation at all).
- **Cookies** — the session cookie is `better-auth.session_token`; `rememberMe: true` sets a `Max-Age` (persists across browser restarts), `rememberMe: false` omits it (expires with the browser session). Verified in `test/auth.e2e-spec.ts`.
- **CORS** — `main.ts` now calls `app.enableCors({ origin: process.env.FRONTEND_URL ?? 'http://localhost:3000', credentials: true })` (added in this pass) so a separate frontend origin can send/receive the session cookie. There was no CORS configuration at all before this.

### 2. Data model fix: `zoneId` is now an integer, not a UUID

The merge originally added `user.zoneId` as a Postgres `uuid` column with a real FK to `zones(id)` — but `zones.id` has been an auto-increment `integer` since an earlier refactor (see `docs/HU-11.md`), so that FK could never actually be created; running the migration would fail outright. Fixed in this pass, consistent with every other id in the codebase:
- `UserOrmEntity.zoneId`: `uuid` → `integer`, type `string | null` → `number | null`.
- Migration `1792641000000-AddUserRoles`: `ADD COLUMN "zoneId" uuid` → `integer`.
- `auth.ts`'s `additionalFields.zoneId.type`: `'string'` → `'number'`.
- `AssignUserRoleDto.zoneId`: `string` (uuid format) → `number`; `AuthController.assignRole` validates with `Number.isInteger` instead of a uuid regex (the regex helper was removed, now dead).
- `README.md`'s role-assignment example updated to `"zoneId": 1`.

### 3. CLI migration runner (`data-source.ts`) restored to globbing

The merge also replaced `data-source.ts`'s documented glob-based `entities`/`migrations` config with a hardcoded explicit list covering only `zones` + `auth` (and incorrectly importing the dead `src/modules/client/` singular entity — see below). That silently dropped `clients`, `catalogs`, `quotes`, and `visit`'s migrations from every `npm run migration:run`, which is why tables like `client_types` never got created and `CatalogsSeedService` failed on boot. Reverted to the original glob pattern (`src/modules/**/infrastructure/*.orm-entity.ts` / `.../migrations/*.ts`) documented in `CLAUDE.md`. **Not yet re-verified against a live Postgres in this environment** — Docker wasn't reachable when this was fixed; re-run `docker compose up` + `npm run migration:run` to confirm `client_types` and the rest now get created.

### 4. Dead stray module removed

`src/modules/client/` (singular — distinct from the real `src/modules/clients/`, HU-11) was deleted. It was never imported into `AppModule`, had no `domain`/`application` layers, a controller that returned the literal string `"hello word"`, Spanish/UUID-style columns inconsistent with the rest of the codebase, and its `@Module` class was even named `ZonesModule` by copy-paste mistake. It was also the thing `data-source.ts` was wrongly importing (see above).

### 5. Entity relations to `clients` (not strictly HU-05, done alongside it)

`quotes.client_id` and `visits.client_id` had no DB-level FK and no application-level existence check — a quote or visit could be created against a nonexistent client. Fixed:
- `QuoteOrmEntity`/`VisitOrmEntity` now declare a `@ManyToOne('ClientOrmEntity') @JoinColumn({ name: 'client_id' })` relation (string-targeted + `import type`, mirroring how `quote-item.orm-entity.ts` already avoids a circular value-import with `quote.orm-entity.ts`, and how `visit.orm-entity.ts`'s own comments already warn about ESM circular-import crashes from bidirectional relations — this one is one-directional and cross-module, so it's a different, lower-risk case; the full unit-test suite was re-run afterward with no import failures).
- New migrations `AddQuoteClientForeignKey` and `AddVisitClientForeignKey` add the actual Postgres FK (`ON DELETE RESTRICT`), consistent with how `client_contacts.client_id → clients(id)` already works. **Assumes no orphaned `client_id` rows already exist** — unverified against a live DB in this environment.
- `CreateQuoteUseCase` now validates the client exists via the shared `ClientReader` port before creating a quote, throwing a new `ClientNotFoundError` (mapped to `404` in `QuotesController`) — this is what actually made the `ClientReader` real adapter below necessary, not just nice-to-have.
- `src/shared/clients/`'s `ClientReader` port — previously bound to `NullClientReader` (always returned `null`, per `CLAUDE.md`'s long-standing TODO) — is now bound to a real `TypeOrmClientReader` backed by `src/modules/clients/`' `ClientRepository`/`ClientContactRepository` and `src/modules/catalogs/`'s `CatalogRepository` (for the potential's display name). `visit`'s `GetVisitByIdUseCase`, which already consumed this port for enrichment, now gets real data instead of always falling back to the bare visit.
- Same gap existed for `clients.zone_id/client_type_id/potential_id/client_status_id`, already flagged in `docs/HU-11.md` ("None of the four are declared as DB foreign keys") — the last three couldn't be constrained until HU-14's catalog tables existed, which they now do. Added `ClientOrmEntity.zone/clientType/potential/clientStatus` relations (same string-targeted pattern) and a new migration `AddClientCatalogForeignKeys` adding all four FKs. **Not done:** application-level existence validation in `CreateClientUseCase`/`UpdateClientUseCase` before insert/update (unlike `quotes`, which now validates via `ClientReader` first) — the DB FK will still reject a bad id, just as a raw constraint-violation error rather than a friendly `404`/`400`. Left as a follow-up given scope.

### 6. Swagger query-param bug

`FindClientsQueryDto.zoneId/clientTypeId/potentialId` and `DashboardFiltersDto.territoryId` are typed `number | string` (to accept raw query-string values before parsing) but had no explicit `type:` on `@ApiPropertyOptional`. `@nestjs/swagger` can't reflect a union type, so it fell back to `object` — Swagger UI rendered these as a JSON editor textarea instead of a plain number input. Fixed by adding `type: Number`, matching the pattern `PaginationQueryDto.page/limit` already used.

### 7. Global session guard

`SessionGuard` is now registered as a global `APP_GUARD` in `AuthModule`'s providers (`{ provide: APP_GUARD, useClass: SessionGuard }`). **Every route in the app now requires a valid session by default** — `zones`, `quotes`, `visit`, `clients`, `catalogs`, previously wide open, are now gated too. Routes that must stay reachable without a session are explicitly marked `@Public()`:
- `AuthController`: `login`, `register`, `logout`.
- `AppController.getHealth()` (`GET /`) — otherwise `test/app.e2e-spec.ts`'s health check would itself 401.
- Swagger's `GET /docs` and Better Auth's native `/api/auth/*` routes needed **no** `@Public()` — both are mounted as raw Express middleware outside Nest's controller/guard pipeline (see the endpoints table above), so the global guard never sees them.

`@thallesp/nestjs-better-auth` (the library backing `auth.ts`) ships its **own** global-guard mechanism (`AuthGuard`, enabled by default, disabled here via `disableGlobalAuthGuard: true`) with its own `@Public()`/`@Roles()` decorators and session-trusting role checks. Deliberately **not** switched to: its `checkUserRole()` trusts `session.user.role` as cached in the session, which directly contradicts this project's own documented design ("roles are read from the database to avoid trusting stale session data", `README.md`'s Roles section) — our hand-rolled `RolesGuard` re-reads from `UserOrmEntity` on every check instead. Registering our own `SessionGuard` as `APP_GUARD` keeps that behavior and avoids running two separate `getSession()` calls per request.

**Known consequence, not fixed in this pass:** every other module's e2e tests (and any manual Swagger "Try it out" call) now need a valid session cookie first — none send one today, since none existed before. Unit tests (`*.spec.ts`) are unaffected; they instantiate controllers/use cases directly and never go through Nest's guard pipeline. `test/auth.e2e-spec.ts` and `test/app.e2e-spec.ts` were re-read against this change but **not re-run** (no live Postgres in this environment this session) — the other modules' e2e suites (`zones`, `clients`, etc., if any exist) weren't audited for this either.

### 8. `AuthController` refactored into use cases

Moved all business logic out of the controller into `application/`, one use case per action — matching the `zones`/`quotes`/`clients` convention (`CLAUDE.md`: "Use case: ... is the only place domain errors are thrown"):
- `LoginUseCase`, `RegisterUseCase`, `LogoutUseCase` — call Better Auth via its own `AuthService` (from `@thallesp/nestjs-better-auth`, globally injectable since `BetterAuthModule.forRoot()` defaults `isGlobal: true`), not the raw `auth` singleton import — real constructor DI instead of a module-level singleton reference, consistent with how every other use case in the codebase takes its dependencies. A shared `extractSetCookies()` helper (`application/extract-set-cookies.ts`) replaces the controller's old private `forwardCookies` cookie-parsing logic; the controller keeps only the thin `res.setHeader('set-cookie', ...)` call, since actually writing an HTTP header is presentation-layer, not business logic.
- `GetCurrentUserUseCase`, `AssignUserRoleUseCase` — the DB-backed logic (`UserOrmEntity`/`ZoneOrmEntity` lookups), each throwing a specific new domain error (`domain/errors/`: `InvalidCredentialsError`, `RegistrationFailedError`, `InvalidRoleError`, `ZoneRequiredError`, `UnexpectedZoneError`, `ZoneNotFoundError`, `UserNotFoundError`) that `AuthController` catches and maps to the same HTTP status codes as before (401/400/404) — external behavior is unchanged, only where the logic lives.
- **Deliberate compromise, not a full port abstraction:** `GetCurrentUserUseCase`/`AssignUserRoleUseCase` still inject `@InjectRepository(UserOrmEntity)`/`@InjectRepository(ZoneOrmEntity)` directly (TypeORM repositories) rather than going through an abstract `UserRepository` port the way `zones`/`clients`/`quotes` do for their own entities. Introducing a full port/adapter layer for tables that Better Auth itself owns and manages the schema of felt like scope beyond what was asked ("extract use cases"); the concrete win this pass delivers is that `AuthController` no longer touches TypeORM at all, and each action's logic + domain errors live in exactly one place. Worth revisiting if/when the auth module grows more use cases.

## Known gaps (not done in this pass)

- **`CurrentAdvisorProvider` was deliberately left on the `x-user-id` header stub.** The audit that prompted this pass suggested replacing it with one reading the Better Auth session, but `README.md`'s own "Roles" section says linking a Better Auth `user` to an `ASESOR`/advisor record is explicitly out of scope for this repo — and there's a real type mismatch besides: Better Auth's `user.id` is a string, while `CurrentAdvisorProvider.extract()` and `visits.advisor_id` are typed `number`. There's no defined mapping between the two today. Swapping the adapter without that mapping would be inventing a design decision, not implementing one — flagging it instead.
- **HU-05 vs. HU-06 overlap** — `PATCH /auth/users/:userId/role` (role assignment) is really HU-06's concern, living inside the HU-05 controller/module. Not split into a separate module in this pass.
- **Other modules' own test suites were not updated for the new global guard.** Their unit tests are unaffected (see above), but if any of them have e2e specs assuming open access, those will start failing with 401 until updated to authenticate first. Not audited module-by-module in this pass.
- Git: `feat/HU-05` was merged into `develop` as commit `257d5fb feat: merge HU-05` (confirmed mid-session; `git log` also shows `819a8d3 feat(auth): partially implement Story 6 role-based access` and `ef43810 feat: better-auth finished` leading up to it). The zoneId-type and `data-source.ts` glob fixes described above are included in that commit. Everything else in this doc (stray-module removal, CORS, DTO validation, the `ClientReader`/quotes/visits/clients relation work, the global guard, and the `AuthController` use-case refactor) is **uncommitted working-tree changes on top of that merge** — not committed, since committing wasn't requested.
