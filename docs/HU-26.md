# HU-26 — Reschedule a visit or mark it as not completed

**Owner:** Camilo · **Epic:** E4 — Agenda, visits and follow-up · **Priority:** Medium
**Source:** `docs/Comercial360_Historias_y_Reparto_v2.pdf`, page 7

> As an advisor, I want to reschedule a visit or mark it as not completed.

## Acceptance criteria

| Criterion | Status |
|---|---|
| Change the visit status and scheduled date when applicable | ✅ Done |
| Record each change in the activity log | ✅ Done |

## What was implemented

### 1. Visit lifecycle

Implemented in the existing `src/modules/visit/` module, following its domain, application, infrastructure, and presentation layers:

- **Domain** — `Visit.reschedule()` and `Visit.markNotVisited()` enforce allowed status transitions. Rescheduling validates the date and preserves actual visit details and results.
- **Application** — `RescheduleVisitUseCase` and `MarkVisitNotVisitedUseCase` load visits scoped to the current advisor, persist valid transitions, and record activity events.
- **Infrastructure** — Reuses `VisitDao` and `TypeOrmVisitDao`; updates the existing `visits.scheduled_at` and `visits.status` columns. The existing agenda query orders visits by `scheduled_at`, so rescheduled visits appear on their new date.
- **Presentation** — Adds validated `RescheduleVisitDto` and Swagger-documented controller operations. Both operations use the existing `CurrentAdvisorProvider`.
- **Module wiring** — Registers both use cases in `VisitsModule`; no parallel repository or activity-log implementation was added.

### 2. Status transitions and historical data

- Visits in `PENDING` or `RESCHEDULE` can be rescheduled. The canonical resulting status is `RESCHEDULE`.
- A `RESCHEDULE` visit can be started through the existing start-visit operation.
- Visits in `PENDING`, `RESCHEDULE`, or `IN_PROGRESS` can be marked `NOT_VISITED`.
- Visits in `VISITED` cannot be rescheduled or marked as not visited. Completed results and history are not overwritten.
- Rescheduling preserves `actualDate`, `startTime`, `endTime`, observations, and results.
- The story and existing model do not prohibit past scheduled dates. The API validates the timestamp format, calendar date, time, and timezone without imposing an additional future-date rule.

### 3. HTTP endpoints

| Method and path | Behavior |
|---|---|
| `PATCH /visits/:id/reschedule` | Reschedule an advisor-owned pending or previously rescheduled visit |
| `PATCH /visits/:id/not-visited` | Mark an eligible advisor-owned visit as not visited |

The reschedule request requires an ISO 8601 timestamp with a timezone:

```json
{
  "scheduledAt": "2026-10-22T14:30:00-05:00"
}
```

The not-visited operation does not require a request body. Both endpoints return the updated visit details and reject missing visits or invalid transitions.

### 4. Activity log

Both operations use the shared `ActivityLogService`, which is wired to the persistent `TypeOrmActivityLogService` and the `client_histories` table:

- `visit.rescheduled` records the visit and advisor, prior and new statuses, and prior and new scheduled timestamps.
- `visit.not_visited` records the visit and advisor, prior and new statuses, and the scheduled timestamp.
- Both events include the visit's `clientId`, allowing the shared adapter to associate the entry with the client's history. The database supplies the event creation timestamp.

Activity-log errors are propagated rather than reported as success. Visit persistence and activity logging are separate operations, however, and are not covered by one database transaction.

### 5. PostgreSQL schema

No migration was needed. The existing `visits` table already stores `scheduled_at` and `status`, and HU-15 provides the shared `client_histories` table. `synchronize` remains disabled; schema changes continue to be managed through migrations.

## Not yet verified

- The full `npm test` suite and `npm run test:e2e` were not run for this story.
- Database-backed HTTP behavior and activity-log persistence were not verified against a live PostgreSQL instance.
- `npm run migration:run` was not run; HU-26 does not add a migration.
- The existing `CurrentAdvisorProvider` reads the temporary `x-user-id` header. Better Auth sessions are required by the app-level guard, but no mapping from a session user ID to the integer advisor ID has been defined. The header must not be treated as a trusted identity source until that integration is resolved.

## Explicitly out of scope

- Changing the shared activity-log contract, persistence adapter, or schema owned by HU-15.
- Adding a reason/observation field or new visit statuses.
