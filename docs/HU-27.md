# HU-27 — Start commercial management from a visit

**Owner:** Camilo · **Epic:** E4 — Agenda, visits and follow-up · **Priority:** Medium
**Source:** `docs/Comercial360_Historias_y_Reparto_v2.pdf`, page 7

> As an advisor, I want to indicate from a visit whether a quote or an order was generated.

## Acceptance criteria

| Criterion                                                            | Status                                                                                                          |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Provide a “Commercial management” section from a visit               | ⏳ Frontend not present in this repository                                                                      |
| Let the advisor choose whether to continue with a quote or order     | 🟡 Quote backend flow is available; order flow and frontend are missing                                         |
| Open the corresponding E5 creation flow with the visit client loaded | 🟡 Backend quote submission is connected to the visit client; frontend navigation and order flow remain pending |

The project specification does not state that quote and order are mutually exclusive, and no implementation establishes that rule. This change does not impose exclusivity.

## What was implemented

### 1. Reused E4 and E5 capabilities

- E4 already exposes `GET /visits/:id`, scoped to the current advisor, and returns the visit's `clientId` and available client details.
- E5 already owns quote creation through `CreateQuoteUseCase`, `POST /quotes`, and the quote repository. The existing create use case validates that the client exists and calculates totals.
- No frontend application and no orders module or order-creation endpoint exist in this repository.

### 2. Create a quote from an authorized visit

Added `CreateQuoteFromVisitUseCase` in `src/modules/quotes/application/`. It verifies that the visit belongs to the current advisor, then delegates quote creation to the existing E5 `CreateQuoteUseCase`. It supplies the visit's `clientId` itself; the request DTO does not accept a client ID. This prevents a visit-originated quote submission from accidentally targeting a different client.

The quote flow is connected through:

1. `GET /visits/:id` loads the visit and client context for the UI.
2. The frontend can open its quote form with that visit context.
3. On explicit form submission, it calls `POST /quotes/from-visits/:visitId` with quote notes and items.
4. The backend resolves the advisor-owned visit, derives its `clientId`, and invokes E5's existing quote-creation use case.

Opening or filling a form does not create a quote; creation occurs only when the POST request is submitted. The quote stores its client ID as usual. The current schema does not store a source visit ID, so this integration does not create a permanent visit-to-quote relationship.

### 3. HTTP contract

`POST /quotes/from-visits/:visitId` requires the existing authenticated application session and the advisor identity consumed by `CurrentAdvisorProvider`. The current provider still uses the temporary `x-user-id` header; a Better Auth user-to-advisor mapping has not been defined.

Example request:

```json
{
  "notes": "Prepared during the client visit",
  "items": [
    {
      "productName": "Laptop Dell Latitude 3420",
      "quantity": 1,
      "unitPrice": 750.5
    }
  ]
}
```

The request intentionally has no `clientId` field. On success, the endpoint returns the existing `QuoteResponseDto` with the visit's `clientId`, generated quote number, calculated totals, and line items. It returns `404` if the visit does not exist or is not owned by the advisor; a missing client is reported through E5's existing `ClientNotFoundError` handling. Invalid request fields are rejected by DTO validation.

The existing standalone `POST /quotes` endpoint remains available and unchanged for quote creation outside this visit-originated flow.

### 4. Module integration and persistence

`QuotesModule` imports the existing `VisitsModule` and `AuthModule` to reuse `VisitDao` and `CurrentAdvisorProvider`. `VisitsModule` does not import `QuotesModule`, so the integration does not introduce a module cycle.

No table, entity, migration, quote-calculation logic, or order functionality was added. E5 remains responsible for quote persistence and totals; E4 remains responsible for determining the authorized visit and its client context.

## Not yet implemented or verified

- The “Commercial management” section and navigation cannot be implemented here because this repository contains no frontend.
- Orders cannot be started from a visit because this checkout contains no orders module or order-creation contract. This requires coordination with E5; no order API or data model was invented here.
- The backend integration creates a quote on submission; it does not provide a form-opening endpoint or persist a source visit ID on the quote.
- Database-backed integration and the full e2e suite were not verified against PostgreSQL.

## Explicitly out of scope

- Implementing the frontend section, quote form, or navigation.
- Creating or modifying order entities, tables, endpoints, or business rules.
- Enforcing whether quotes and orders are mutually exclusive.
- Persisting a new visit-to-quote relationship.
- Reimplementing E5 quote creation, validation, numbering, totals, or persistence.

## Context accumulated for the E4 presentation

- E4 supplies the advisor-scoped visit lookup through `VisitDao.findByIdAndAdvisor()`.
- E5 owns quote creation through `CreateQuoteUseCase`; the new visit-originated use case delegates to it rather than duplicating commercial logic.
- The visit is the source of truth for the client ID during quote submission; the request cannot override it.
- The repository has no frontend and no order flow, so the UI and order portions of HU-27 remain dependencies rather than completed criteria.
